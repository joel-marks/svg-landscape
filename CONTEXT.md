# SVG Landscape Generator — Project Context

## 1. Overview
One-page web app generating procedural 2D landscape SVGs (noise/algorithmic-based). User tweaks parameters via a control panel, downloads the resulting SVG and/or a settings file. No backend, no accounts, no server. Deployed via GitHub Pages. Rebuilt from scratch — no code ported from prior "Mountain Valley" prototype, though its concepts (aspect scaling, archetype-per-generator, palette engine, mist/sky layering) carry forward as reference.

Two things about the follow-on moves differ from 6.12 and are worth recording: the **foreground tokens did not need to move this time** (they only ever sit on `--surface-raised` or `--surface`, and a lighter raised surface can only improve dark-on-light contrast — every measured pair went up, see section 11), but **`--tp-input-border-color` did**, in the opposite direction to everything else. It is calibrated *to* ~2.9:1 against the field it outlines; left at 6.12's `#3f444a` it would have jumped to 4.9:1 and drawn a hard frame around every input, the opposite failure from the one it was added to fix. It is now `#5b636b`, restoring 3.0:1. Dark mode is untouched, confirmed by reading its computed tokens back before and after.

- **No markdown library.** The Help, Read Me and About modals render markdown through `src/markdown.js`, ~200 lines written for this project in Phase 6.9. It covers the constructs these documents actually use — counted against real content, not guessed: headings, bold, italic, inline code, links, ordered and unordered lists, blockquotes, fenced code blocks and tables. A general CommonMark implementation is a large dependency for three modals, and the failure mode of a small renderer is the right one: unsupported syntax renders as its own literal text rather than breaking. Escapes HTML before inserting any tag, and lifts code spans out before the inline rules run so `**text**` inside backticks stays literal.
- No routing, no state-management library — a single plain state object is sufficient.

```
  help.js                 Help / Read Me / About modals — sources three .md files, open/close, nothing else
  /help

  theme.js                 UI light/dark theme, prefers-color-scheme, persistence
  utils.js                 shared geometry helpers: feature-density/aspect width scaling, common spur/wall primitives used across archetypes, EDGE_BLEED (section 18)
  /archetypes
    open-valley.js, valley-floor.js, v-valley.js,
    gorge.js, in-gorge.js, mountain-top.js, stacked-ridges.js,
    dominant-peak.js, twin-peaks.js
    index.js            registry mapping name -> generator module
/public                favicon, static assets
index.html               single page, semantic landmarks, meta tags. **Phase 6.12**: footer removed; header gains a top-right GitHub icon (inlined SVG) and the build-time git short commit hash, replacing `package.json`'s uninformative `0.0.0`. The hash is a `__COMMIT_HASH__` constant declared in `vite.config.js`'s `define` from `git rev-parse --short HEAD`, evaluated once at build/dev-server start (falls back to `unknown` outside a git checkout rather than failing the build), and written into the header by `main.js` — Vite's `define` substitutes into modules, not into index.html, so the markup carries an empty `#build-hash` span and JS fills it.
```

Each archetype module owns its own generation logic (not shared parameters over one generator) and exports `generate(params) -> geometryItems`. Every `generate()` signature accepts `elevation`, `peakCount`, and `sharpness` (see sections 5, 6a) even where a given archetype treats one as a no-op (e.g. Twin Peaks ignores `peakCount`) — keeps the schema stable as effects are extended to more archetypes later.

"V valley" and its former "rising" variant are merged into one generator driven by the elevation parameter (section 6a) rather than two separate archetypes.

## 5. Control panel — grouped logically

Entirely Tweakpane — title-less Pane instances, folder titles the only headings, no separate HTML/Tailwind panel chrome. One pane per column was the original rule; both outer columns now stack two (Presets over Canvas/Scene on the left since 5.7, Actions over Preferences on the right since 6.6), which is how a group says it stands apart from the ones around it. Renders below the canvas, not beside it (still required — X-Pan 2.71:1 and LinkedIn 4:1 rule out a side panel). Three columns:
- **Left** — Presets (its own pane, stacked on top), then Canvas (Aspect ratio is the first control below it), Scene
- **Centre** — Lighting, Color
- **Right** — Actions, then Preferences — **one Pane instance each** since Phase 6.6, stacked the way the left column already stacks Presets over Canvas/Scene. They were two folders sharing one pane through Phase 6, which read as a single panel with two sections rather than the two separate things they are: Actions is what you do with the scene, Preferences is how the app behaves.

Folders are collapsible (accordion) — this was tried flat in one revision and deliberately reverted back to accordion for a tighter footprint, given window-size constraints on a desktop-first layout. Color's centre-column folder is a readonly Tweakpane note ("Arrives in Phase 5") until Phase 5 lands — not stubbed sliders, which would wrongly imply they work. Actions is a Tweakpane folder like the others — it carries no bespoke chrome — but sits in a pane of its own since Phase 6.6. Tweakpane buttons are text-only — Lucide icons are no longer used inside the panel, only in page chrome outside it (header, etc.).

Header/nav side margins align with the canvas and panel-grid side margins. One `.shell` class defines that gutter; it was shared by header, main and footer through Phase 6.11 and is shared by header and main from 6.12, the footer having been removed. Dropping a consumer changes nothing about what the class computes to, and the convention was re-measured after the removal rather than assumed: header and main resolve to identical left and right edges (80px / 1360px at a 1440px viewport).

**Phase 6.12 — input visibility**: Tweakpane sliders, text fields and checkboxes were near-invisible against the panel background and now carry a pale, theme-appropriate 1px border, correct in both UI themes. The intended route was Tweakpane's own custom-property theming; **it does not exist for this**. Checked against the stylesheet Tweakpane 4.0.5 actually ships (`node_modules/tweakpane/dist/tweakpane.js`) rather than assumed: its theming API is exactly the `--tp-base-*`, `--tp-button-*`, `--tp-container-*`, `--tp-groove-*`, `--tp-input-*`, `--tp-label-*` and `--tp-monitor-*` names already used in `style.css`, and there is no border property among them. So this is the prompt's stated fallback — a scoped override on Tweakpane's own input classes (`.tp-txtv_i`, `.tp-ckbv_w`, `.tp-sldv_t::before`, `.tp-sldv_k::after`, plus the readonly monitors `.tp-sglv_i` / `.tp-mllv_i`), coloured from one new `--tp-input-border-color` token defined per theme so the two skins stay a single definition. The slider *rail* is a 2px `::before` that a border would consume outright, so it takes a 1px spread `box-shadow` instead.

Those override rules sit **outside every cascade layer**, deliberately. Tweakpane injects its stylesheet as a plain unlayered `<style>` at runtime, unlayered beats any layer regardless of specificity, and its own reset sets `border-width: 0` on every one of those elements — the same rules written inside `@layer base` would never paint. That is exactly the failure that kept the canvas frame's inset ring invisible for eight phases (section 18), so it was avoided by construction in the phase that fixed it. Unlayered against unlayered, `.tweakpane-scope .tp-*` (0,2,0) beats Tweakpane's `.tp-*` (0,1,0) on specificity and is independent of stylesheet order.

**Phase 6.13 — brighten raised surfaces, optically verified**: `--surface-raised` (header/nav, panel chrome) moved from 60% to **76%** lightness (`#94999e` → `#bfc2c5`), judged against real before/after screenshots rather than a computed target, per Joel's explicit instruction. The whole Tweakpane light scale moved with it — the same +16 points on every step, each keeping its own hue, saturation and relative spacing, so the shape (base lightest, then input, container, groove, button, each interaction state a step darker) is exactly the one 6.12 established and only its position changed: base 76%, input 71.9%, container 71.1%, groove 64%, button 63.1%. `--surface` and `--surface-sunken` did not move. The full account of what else moved, what didn't, and why is in section 2; the re-measured contrast is in section 11.

**Phase 6.13 — Time of day as a dial, tried and rejected**: `@tweakpane/plugin-camerakit`'s `cameraring` was built alongside the linear slider so the two could be compared live. It worked — unconstrained so midnight was continuous rather than a clamp, kept in sync from `refresh()`, verified wrapping in both directions — and it was **still the wrong control**, because a `cameraring` is a lens focus ring seen edge-on, a horizontal scale scrolling past a fixed marker. Both it and the slider were removed in Phase 6.14. Recorded rather than deleted because the trial did its job: building it is what made clear that "rotary" and "a clock face" are not the same request.

**Phase 6.14 — Time of day is a clock face, and the only control for it**: a literal 24-hour clock — a circle, a tick on every hour, and a hand joining the centre to the edge. One revolution is 24 hours, not 12. It is the **first control in Lighting**, above Show sun/moon, and the linear slider and the cameraring are both gone.

*As built.*
- **Noon at the top, midnight at the bottom, clockwise.** Deliberately *not* how a clock reads — 00:00 at the top would be — because this control drives a sun. 06:00 lands at the left where the sun rises in the frame, 12:00 at the top where it is overhead, 18:00 at the right where it sets. The hand is a picture of the sky rather than a picture of a clock. Joel's choice, made from a side-by-side of both orientations. Verified by clicking the four cardinal points: top 12.00, right 18.00, bottom 0.00, left 6.00 exactly.
- **Absolutely positioned, so midnight needs no special case at all.** The hand goes where you point; `atan2` cannot return a value outside one revolution, so the wrapping machinery the cameraring needed — a proxy value free to run past 24, a wrap applied on drag-end, a mid-drag flag suppressing the sync — is simply **absent**. The clock binds straight to `state.hour`. Confirmed by dragging across the bottom of the face: 00:56 to 23:04, straight through midnight, no stop.
- **Not a Tweakpane binding**, so two things had to be handled by hand. It is written from `refresh()`, the one choke point every other source of a change already routes through (presets, Reset to defaults, the localStorage restore — all three tested in both themes). And it checks the `syncing` flag itself, since it does not get `onUserChange()`'s guard for free.
- **Mounted after every Tweakpane control in the folder, then prepended.** This ordering is load-bearing, and the first attempt got it wrong: Tweakpane inserts each blade at its own index into the container's child list, counting only the blades it knows about, so a foreign element sitting at index 0 gets stepped over by every subsequent insert and ends up **last**. Prepending once the folder is otherwise complete is what actually puts the clock first. Safe at construction either way, since Tweakpane caches a folder's expanded height on the first collapse and that cannot have happened yet — verified by collapsing and reopening Lighting and measuring no clipping.
- **Keyboard operable**, which an SVG gets none of for free (section 11): `role="slider"` with `aria-valuetext` carrying the clock reading rather than the decimal, arrows ±0.1h to match the panel's other steps, Shift/PageUp/PageDown ±1h, Home 00:00, End 12:00, and a focus ring drawn round the face rather than a box round the element.
- **Themed entirely from `--tp-*` tokens**, so Light/Dark/System keep resolving through the one code path, with the rim reusing `--tp-input-border-color` so it carries the same outline the text fields got in 6.12. Depending on Tweakpane's own class names for the row layout is the already-established pattern here, not a new liberty — the 6.12 input borders do exactly the same against a pinned 4.0.5. The styling sits **unlayered** with those rules for the same documented reason (section 18).
- **No numeric readout.** One was built and then removed at Joel's instruction — the face is the control, and a second field restating it was scope that was not asked for. Consequence to be aware of rather than a defect: the panel no longer displays the exact hour anywhere, so 18:30 and 18:36 are not distinguishable by eye. Reinstating a readout is a small change if that ever bites.

**Phase 6.13 — Time of day readout fixed (unplanned).** `03:00` displayed as **`02:60`**. Tweakpane's step constraint can land a typed 3 on 2.999999999999999 (the ulp in section 18), and the formatter took the hour and the minute off the value independently — `Math.floor` took the hour down to 2 while `Math.round` took the minutes up to 60. Pre-dates this phase; found while checking the dial against the slider, and fixed in the formatter they shared, which rounds to whole minutes first. Both of those controls were removed in 6.14, but the formatter survives them — the clock face uses it for its screen-reader value. The stored value keeps its ulp, exactly as the Phase 6.5 preset-matching fix left it — this corrects what is shown, not what is held.

**Presets panel** (Phase 5.7, preset-loading mechanism finalized Phase 5.12) — a separate Tweakpane instance from the below-canvas control panel, stacked at the **top of the left column**, above Canvas/Scene. Same gutter-alignment discipline as everything else (nav/canvas/panel margins match). Titled **"Presets"** since Phase 6.6 — it had been the one unnamed panel on the page since 5.7, and the heading is a folder like every other heading in the panel rather than a Pane title, so it collapses the same way. Contains a dropdown labelled **"Load preset"** defaulting to "Custom," followed by the curated preset list; the label distinguishes it from the Downloads tab's "Preset name" field, which labels a scene on its way *out* rather than selecting one to bring *in*. Beneath it, separated by Tweakpane's own separator blade (Phase 6.7 — the panel's own vocabulary rather than a CSS margin standing in for it), sits **Reset to defaults**, relocated from Actions in Phase 6.6. Both controls answer "what should the whole panel be set to," so they belong in one panel; the rule between them says they are not the same gesture — one loads a saved scene, the other discards the current one. Preset source: a `src/presets/*.json` folder, auto-discovered at build time via Vite's `import.meta.glob('./presets/*.json', { eager: true })` — no manifest file, no code change needed to add one, just drop a `.json` file in the folder and commit. Each preset file is the exact same shape as a "Download JSON" export (section 8), including the Preset name field — so authoring a preset is: configure a scene, name it in the Downloads tab, Download JSON, move that file into `src/presets/`. Dropdown label uses the file's embedded name field; falls back to a filename-derived label if that's missing, rather than breaking the list. Selecting a preset loads its full parameter set and regenerates; the dropdown returns to "Custom" whenever the live state doesn't match a saved preset (including on any manual control change after a preset was loaded). No in-app "save current as preset" capability yet (folder-drop is the authoring path for now; flag if that scope should expand). Defaults to **"Custom"** on first load — verified in the live app in Phase 6.12, not assumed: with localStorage cleared the `<select>`'s value reads `Custom`, and neither curated preset matches the new factory defaults.

**Canvas fit/sizing model** (previously underspecified — this caused a regression once, don't let it happen again): the canvas container is full available width within the shell's gutters, height derived via CSS `aspect-ratio` matching the current viewBox ratio, capped by a **fixed 740px** max-height (not viewport-relative — a `vh`-based cap reintroduces bars on shorter screens, which is what happened in Phase 4.6). Letterbox/pillarbox bars should appear **only** when that fixed cap is the actual binding constraint (4:3 at larger viewport widths is the one preset this currently affects, by design) — every other aspect, including 16:9 and the wide presets, fills its container edge-to-edge with no bars. The SVG fills its frame flush to the edges with no inset padding, and is clipped to match the frame's rounded corners rather than floating inside a visible gap. If bars appear on an aspect that isn't hitting the height cap, or the image doesn't reach the frame edge, that's a bug, not expected behavior.

**Canvas**
- Aspect ratio (dropdown: 4:3, 16:9, Cine 2.39:1, X-Pan 2.71:1, LinkedIn 4:1)
- Feature density auto-scales with canvas width (wider aspect → proportionally more ridge/spur features, never fewer)

**Scene**
- Landscape type (dropdown)
- Complexity (slider — noise octave count / point sampling density only. Controls detail resolution — how fine or coarse the terrain silhouette is — not feature count. See Peak count below for that.)
- Peak count (slider — number of peaks/spurs/ridges, independent of Complexity. Normalized 0–1 like Complexity/Elevation; each archetype maps it to its own sensible integer range. No-op on archetypes where a fixed count is the defining trait (Twin Peaks' 2, Stacked Ridges' band count) or where the concept doesn't apply.)
- Peak sharpness (slider — blends the terrain profile between smooth/rolling and jagged/ridged. 0 = rounded hills, 1 = sharp ridgelines.)
- Point of view height (slider, global — see section 6a. Active on all archetypes except In Gorge, which is a deferred edge case; disabled/labelled accordingly there. Quality varies by archetype — see section 6a's note.)
- Seed value (display + lock). **Default: locked.** Lock guards against *incidental* reseeding from other Scene/Canvas control changes (landscape type, complexity, peak count, sharpness, elevation, aspect ratio) — with it on by default, tweaking those sliders no longer reseeds unless explicitly asked to. New View always draws a new seed regardless of lock state — the one control whose purpose is to change the seed isn't disabled by it.
- **New View | Random all | Random scene** (Phase 6.7 — consolidated into one button-grid blade, three cells in this order):
  - **New View** — the original reseed action: draws a new seed, keeps every other parameter.
  - **Random all** (new, middle cell) — both at once: draws a new seed *and* redraws Complexity, Peak count, Peak sharpness and Point of view height. Same underlying logic as the other two combined, not a third separate implementation.
  - **Random scene** (introduced Phase 6.6, moved into this row Phase 6.7) — the mirror of New View: redraws Complexity, Peak count, Peak sharpness and Point of view height to fresh values in their existing ranges while keeping the seed. Landscape type is deliberately excluded from all three — rerolling the archetype too would make this a "surprise me" for the whole panel, and the archetype is the one Scene choice a user has usually already made on purpose. Seed lock does not block any of the three, for two different reasons: Random scene never reseeds at all, so there is nothing for the lock to suppress; New View and Random all reseed *explicitly*, and the lock guards only against **incidental** reseeding — a control whose stated purpose includes drawing a new seed is not silently disabled by it (same rule as the Seed bullet above).

**Lighting**
- Time of day (**24-hour clock face as of Phase 6.14**, the folder's first control; a linear 0–24 slider before that) — drives sky gradient, mist tint, sun/moon crossfade, star field opacity, and (Phase 6.13) the sun's colour and the moon's size — see section 6c. See the panel note above for the face's orientation and why it is hand-built.
- Show sun/moon (toggle) — hides the celestial disc and its glow only; no effect on sky/mist lighting itself
- Show stars (toggle) — independent of the above; hides the night star field only. The field itself is a **fixed backdrop** (Phase 6.5): star positions are generated once, per scene seed, against a reference frame no control can move — the canvas height by the widest supported aspect — and then clipped to the current canvas. Nothing about the scene rescales it. Raising the horizon with Point of view height simply reveals less of the same field, by ordinary draw-order occlusion (terrain paints over the sky). A wider aspect reveals *further into* the field, so star count rises with width at constant density, consistent with the Canvas feature-density convention — but no existing star moves. See section 18 for the bug this replaced.
- **Shadow / pseudo-3D toggle — default: ON as of Phase 6.12** (previously off). See section 6 for the new default-state relationship with time of day.
- Light source angle (slider, active when shadow on — independent of time-of-day by default, see section 6)
- **Lock angle to time of day — default: ON as of Phase 6.12** (previously off; "tidelock," see section 6)
- Shadow intensity (slider, active when shadow on — non-linear response, see section 6b)

**Color**
- Theme preset (dropdown, curated palettes — 7 as of Phase 5: Alpine dusk, Glacier, Cascade pine, Sandstone mesa, Volcanic ash, Heather moor, Ink wash). A button-grid blade directly beneath it: Previous | Randomise | Next, in that order. Previous/Next cycle the curated list only (wraps at both ends, not through "Randomized"); Randomise is the existing algorithmic generator from Phase 5. Replaces the Phase 5.5 vertically-flanking buttons — this needed the Tweakpane essentials plugin to lay the three out in one row (see section 2).
- Color depth (slider — controls contrast between near and far layers in ramp-position space: compression toward the palette midpoint below 0.5, an S-curve spreading toward the ramp's extremes above 0.5. 0.5 is the theme as authored. Not a literal band/posterize count, and not endpoint extrapolation — that was tried and clamps out near the top of the range.)
- Distance haze (slider — horizon-level atmospheric mist band: opacity/spread only. Lighting owns the tint via time-of-day; Color owns this band's presence and shape.)
- Valley mist (slider, Phase 5.10 revision — renamed from Ridge mist, rebuilt three times: crest-topology mechanism (5.6) → simple per-layer vertical fade to a shared canvas-bottom anchor (5.8) → depth-aware grading with foreground exclusion and layer-linked color (5.9) → per-layer bottom anchor corrected (5.10). Mechanism per layer, except the nearest/foreground layer which is always fully excluded — no mist on it at any slider value, not just a low amount. Each remaining layer gets a vertical fade: 0% opacity at that layer's own single highest crest point, increasing to that layer's scaled maximum opacity at **that layer's own bottom anchor** — the next-nearer layer's peak Y (the true-foreground layer's peak, for the nearest misted layer), not the shared canvas bottom used in 5.8/5.9. Guard: falls back to the 5.9 canvas-floor anchor when the occluder's peak isn't below this layer's own peak — this happens on Open valley, In gorge, and partly Gorge, where near layers reach the top of frame; those three archetypes don't get 5.10's benefit, they just don't break. Everything else unchanged from 5.9: userSpaceOnUse, the `<use>` reuse trick, section 6b's response curve, per-layer distance-scaled ceiling (Distance control), and per-layer color-derived mist tone.)
- Distance (slider, Phase 5.9) — controls how strongly Valley mist's per-layer intensity scales with distance. At 0: all non-excluded layers get equal mist intensity (foreground exclusion still applies). ## 6. Pseudo-3D / shadow model
Each hill/peak polygon is split into a light-side and dark-side sub-path along an internal ridge boundary — distinct from the silhouette boundary against the sky. Boundary position and shadow-side is derived from the light source angle. This is treated as its own build task, not a simple style toggle.

Light source angle is directly user-controlled, not slaved to the time-of-day slider by default — the two are independent so shadow direction and sky mood don't fight each other. A sensible default angle may be derived from time-of-day on load, but the slider doesn't auto-follow it afterward — **unless "Lock angle to time of day" is engaged.** Enabling it captures the current offset between the light angle and the time-of-day-derived sun/moon arc position; from then on the light angle rotates automatically to preserve that offset as time-of-day changes — both rotate together, phase fixed, like a literal tidelock. While locked, the Light source angle slider becomes a read-only display of the derived value rather than directly editable, to avoid two controls fighting over the same value. Disengaging the toggle returns the angle to direct manual control at its current (locked) position, not back to whatever it was before locking.

**New default state, Phase 6.12**: Shadow is on and the tidelock is engaged by default (both were off before). The offset is set so that **light source angle reads exactly 0° at time of day 05:40** — computed from the actual sun/moon arc formula in `lighting.js`, not a hand-picked number — and then applied at whatever the real default time-of-day value is (unchanged by this phase; 05:40 is only the reference point defining the relationship, not the new default hour). Because Shadow was off before, there is no prior default shadow appearance to preserve — this is the first time the default scene has ever shown one. The default time-of-day value, sky, and palette are untouched; the tidelock relationship is the only new thing, and the rendered angle at the real default hour is the mechanical consequence of that one relationship, not a second, separately-chosen value.

*As built.* `state.js` holds `ANGLE_ZERO_AT_HOUR = 5 + 40/60` and derives `DEFAULT_ANGLE_OFFSET = normalizeAngle(0 − suggestedAngle(ANGLE_ZERO_AT_HOUR))` by calling `lighting.js`'s exported `suggestedAngle` — the same function the tidelock tracks through, so the two cannot drift if the arc is ever retuned. At 05:40 the sun is below the horizon, so the moon branch supplies the direction: `u = ((5.667 − 18 + 24) mod 24)/12 = 0.9722`, `lerp(180, 0, u) = 5°`, giving an **offset of 355°**. Carried to the unchanged default hour of 18.5, `suggestedAngle(18.5) = 173°` and the panel opens with the angle reading **168°**. Both the first-visit defaults and Reset to defaults come from that one computation, not two: `FACTORY_DEFAULTS` is a snapshot of the same state literal, and `angleOffset` is one of the keys it restores. One caveat found in testing and left alone: Time of day had a 0.1h (6-minute) step, so 05:40 itself was not a reachable slider position — the nearest reachable step, 05:42, is where the readout showed 0°, and it was the only step in a full 0–24 sweep that did. **Phase 6.14 removes the caveat without touching the relationship**: the clock face resolves to the nearest minute rather than to a 0.1h grid, so 05:40 is an exactly reachable position by dragging, and the angle reads 0° there. (Its arrow keys still step 0.1h, so arrowing from a 0.1-aligned value still steps over it — the caveat survives for that one input method, not for the control.)

## 6a. Point of view / elevation model
A global `elevation` (0–1) parameter simulates viewer height, interpolating horizon position and how tightly nested features converge toward the viewer — low elevation reads as ground-level (features fan out, horizon low), high elevation reads as looking down into a landscape (horizon rises, features nest tighter, e.g. converging valley spurs). Meaningfully implemented across all nine archetypes except In Gorge, which is treated as a deferred edge case — its foreground-wall composition doesn't have an obvious viewer-height analog yet and needs separate design thought.

Confirmed (Phase 5.12-era testing) not a bug: the effect reads well on some archetypes and weakly on others. That's per-archetype quality variation, not a defect — see section 13a for how this class of issue is tracked going forward.

## 6b. Non-linear slider response
Some sliders need more usable resolution at one end of their travel than a linear 0–1 mapping gives — Shadow intensity's most visually meaningful range sits in roughly the first quarter of the slider, and Valley mist is deliberately near-invisible through most of its travel, becoming noticeable only near the top. Rather than special-casing each one, the underlying parameter is driven through a shared response-curve mapping: the *displayed slider* stays a normal linear 0–1 drag control, but a power/ease curve maps that linear position to the value actually used in rendering, concentrating resolution where it's needed. One reusable utility, applied to both Shadow intensity (more resolution at the low end) and Valley mist (suppressed through most of the range, ramping up near the top) — not two one-off mappings.

## 6c. Sun and moon appearance (Phase 6.13)
The sun disc and its glow were a fixed colour at every hour prior to this phase — reported by Joel directly ("optically it appears the same color at all times of day"). Position and glow radius already varied with the solar-altitude term computed for body placement; colour did not.

Confirmed in the code before building anything, not assumed: `render.js` filled the sun disc with a literal `#fff6de` and its glow gradient with a literal `#fff3d4`, at every hour.

**Sun colour ramp — built.** A `SUN` table in `lighting.js`, hour-indexed and hand-tuned exactly like `SKY`, not a physical scattering simulation. Pale near-white through the middle of the day (`#fffbf1` at 13:00), a **subtle** gold at sunrise (`#ffca81` at 06:30), and a **much more pronounced** amber-into-red-orange at sunset (`#ffc478` at 17:00, `#fa8d42` at 17:30, `#ea5e28` at 18:00). Deliberately asymmetric, matching the sky table's own stance that dawn and dusk aren't colour mirrors of each other.

Two implementation notes worth keeping. First, `blendSky`'s keyframe lookup was **extracted into a shared `keyframesAt(table, hour)`** used by both tables rather than duplicated, so the sun and the sky cannot interpolate differently; both mix in Lab, so a warm keyframe and a pale one blend through the intermediate warms instead of desaturating through grey. Second, the keyframe *hours* had to be pulled inward after a first pass put the strongest tones where nothing could see them: the disc's own opacity is already under 0.3 by 18:00 and gone by ~18.4, so a red-orange keyframed at 18.3 only ever rendered on a sun that had almost finished fading. Both warm ends now land while the body is still above 0.9 opacity. This is the kind of thing only a sweep catches — the first table was correct by its own description and wrong on screen.

The glow takes the **same value** off the same ramp as the disc, not a related one, so the two cannot drift into a red disc inside a yellow halo. Verified across a 0–24 sweep at 0.5h steps: 25 distinct sun disc colours, and zero steps where the glow differed from the disc. Moon colour is unchanged and was measured to be so — one disc colour (`#eef3fb`) and one glow colour (`#dfe8f5`) across the whole sweep, the same two constants it had before.

**Moon size near horizon — built.** It was trivial: `moonAltitude` is already 0 at the horizon and 1 at the top of the arc, so the radius is multiplied by `1 + 0.28 * (1 - clamp01(moonAltitude))` and rise and set both get it from the one term that already places the body. Nothing new tracks time. The glow follows automatically, since `render.js` derives the glow radius from the disc's. Measured over the same sweep: radius 22.46 at midnight to 28.75 at rise and set, the intended ~28%. Subtle by design — an approximation of the moon illusion, not a physical effect.

## 7. Persistence (localStorage)
Used generally for user preferences, not just theme:
- UI theme
- Tips enabled/disabled
- Last-used control values (restored on load) — the full scene/panel state, not just preferences. Reuses `SETTINGS_KEYS` (the same shape as a settings export, finalized Phase 5.12) as the save/restore shape rather than a separate persistence format. Saves on every control change; restores on load before first render, including the seed itself — a returning visitor sees the exact scene they left, not just the same parameter values with a fresh random seed. Falls back to factory defaults only when nothing is saved yet (first visit) — as of Phase 6.12, those factory defaults include Shadow on and the tidelock engaged (section 6).

Built in Phase 6 as **two keys, not one**: `svg-landscape:state` for the scene/panel blob and `svg-landscape:theme` for the UI theme, which theme.js has owned since Phase 2 and keeps — the theme is an interface preference rather than part of the scene, and has to be readable before the scene state loads. The scene blob is a strict *superset* of a settings export, not a second format: the export's keys verbatim, plus `seedLocked`, `presetName` and `tips`, the three panel values that are deliberately not in `SETTINGS_KEYS`. Saving is hooked to the panel's own post-change refresh rather than added to each handler, so "saves on every change" holds by construction. A corrupt or hand-edited blob falls back to defaults rather than erroring, and individual values whose type doesn't match the factory default's are skipped — unknown *values* of the right type are already safe, since the archetype, theme and aspect lookups each fall back on their own.

## 18. Known issues

**Open**
- *(None as of Phase 6.14. The 6.13 dial's keep-or-drop decision, open in the last revision of this document, was closed by Joel in 6.14: dropped, along with the linear slider, in favour of the clock face.)*

**Closed**
- Time of day displaying `03:00` as **`02:60`**. The formatter took the hour and the minute off the value independently — `Math.floor(v)` for the hour, `Math.round((v % 1) * 60)` for the minutes — so a value carrying the Tweakpane step-constraint ulp described below (2.999999999999999 for a typed 3) had its hour floored down to 2 and its minutes rounded up to 60 at the same time. Reachable from the panel since the format was added, not introduced by any recent phase; surfaced in Phase 6.13 while checking the new dial's readout against the slider's, and fixed there because the two controls now share one formatter. It rounds to whole minutes first and derives both fields from that. **Only the display was changed** — the stored value keeps its ulp, the same call the Phase 6.5 preset-matching fix made, since that ulp is invisible in the render (~1e-17) and in the exported settings.
- The canvas frame's 1px inset ring never painted. `style.css` set `box-shadow: inset 0 0 0 1px var(--border)` on `#canvas-frame` inside `@layer base`, but `index.html` also carries Tailwind's `shadow-sm` utility on the same element — and cascade layers are resolved before specificity, so the utilities layer won over base no matter that the base rule was an id selector. Confirmed by reading `getComputedStyle(frame).boxShadow` in the live app: only `shadow-sm`'s two outer shadows were there, no inset ring. Found while diagnosing the right-edge band in Phase 6.10 and left alone then, correctly — it is **not** a cause of that band (the ring sits behind the SVG either way) and folding it into an unrelated fix would have muddied both. Harmless in the meantime because the SVG covers the frame edge to edge, which is exactly why it went unnoticed from Phase 4.6 to 6.10.

  Fixed in Phase 6.12 by moving the ring onto the element as `inset-ring-1 inset-ring-border-token` and deleting the declaration from `style.css` rather than reordering layers. Tailwind's ring utilities exist for this: `inset-ring-1` writes `--tw-inset-ring-shadow` and `shadow-sm` writes `--tw-shadow`, and both then set the same composite `box-shadow: var(--tw-inset-shadow), var(--tw-inset-ring-shadow), var(--tw-ring-offset-shadow), var(--tw-ring-shadow), var(--tw-shadow)` — so they compose instead of one overwriting the other, whichever the browser applies last. Verified in the live app in both themes: the computed `box-shadow` now carries the 1px inset ring in `--border`'s colour *and* `shadow-sm`'s two outer shadows (light `rgb(52,56,61)`, dark `rgb(39,50,59)`).

  The general lesson was applied again immediately, in the same phase: the new Tweakpane input borders (section 5) are written **unlayered** precisely because Tweakpane's own injected stylesheet is unlayered and would have beaten them from inside `@layer base`, which is this bug with the roles swapped.
- Two scrollbar tracks on the modals. Reported on About, visible on Read Me, and present on **all three** once measured — they share `modal.js`. Two independent causes. First, Read Me nested a scrolling `<pre>` inside the already-scrolling modal body, so it had two vertical tracks at any size. Second, and the general one: the body was capped at a fixed `70dvh` while the dialog was capped at `90dvh`, so once the header and footer were added the body could exceed the shell — and a `<dialog>` defaults to `overflow: auto`, so the shell scrolled too. Measured to appear below roughly 560px of viewport height (About needed ~460px, its content being shorter). Fixed in Phase 6.9 by making the shell a clipped flex column and sizing the body as the remaining space, so it cannot overflow its parent; verified at six viewport heights from 1000px down to 360px. A third track — horizontal, from the README's wide tables — was removed at the same time by wrapping table cells and code blocks rather than letting them scroll sideways.
- The Presets panel's documented position ("between the header and the canvas frame") never matched where it was actually built (top of the left column, since Phase 5.7). Noticed in Phase 6.6, left unresolved pending a decision on which was wrong; resolved in Phase 6.7 by correcting the documentation to match the working, unchanged UI rather than moving it.
- Star field distorting with Point of view height (and, unreported but confirmed in the same pass, with Aspect ratio). Diagnosed before patching, and it was **not** the shape-distortion mechanism: stars are `<circle>` elements with a scalar radius and no transform anywhere up the tree, so no star ever became an ellipse. It was **pattern redistribution** — `starField()` placed every star as a fraction of two references that other controls move: `y = random() * horizonY * 0.94` and `x = random() * width`. Raising the horizon therefore squashed the whole field vertically (measured on a fixed seed: one star at y=438.8 at elevation 0, y=316.2 at 0.5, y=193.6 at 1) and a wider aspect stretched it horizontally (the same star pinned to 92.93% of the canvas width at every aspect, so the pattern spread instead of extending). Fixed in Phase 6.5 by decoupling generation from the horizon entirely and generating against a fixed reference frame, then clipping — see section 5's Lighting group. Verified by measurement, not by eye: bit-identical star lists across a nine-step elevation sweep, and every aspect's field a strict subset of the widest one at identical absolute coordinates. Cost: the field now covers the full frame height rather than stopping at the horizon, so a night scene carries roughly twice the circles and a widest-aspect export grows ~7%; stars hidden behind terrain are not culled from the file.
- Preset matching broken by an ulp. Tweakpane's step constraint is `origin % step + round((value - origin) / step) * step` with **origin fixed at the value the pane was constructed with**, so a value written back through a slider that has since moved can land an ulp off — 0.5 arriving as 0.49999999999999994. `currentPresetId()` compared with `===`, so a scene could stop matching the preset that had just set it and drop the dropdown to "Custom". Closed in Phase 6.5 with a 1e-9 tolerance on numeric comparison in `sameValue` — far below the panel's finest step (0.01) and far above the ulp being absorbed. Note what this did **not** change: Tweakpane still writes those values, so the persisted blob and a settings export can still carry `0.49999999999999994`. That is invisible in the panel (2dp) and in the render (~1e-17); only the consequence needed fixing.
- Canvas fit/sizing bug (bars appearing on aspects that shouldn't have any). Root cause was not a repeat of the Phase 3.6 width fix — it was a `vh`-relative max-height cap binding at typical viewport heights (e.g. 522px on a 900px-tall viewport), forcing 16:9 to letterbox inside a too-short frame. Fixed in Phase 4.6 with a fixed 740px cap (see section 5). Recorded here rather than deleted since it was initially misdiagnosed as the earlier issue — worth not rediscovering.
- Tweakpane panel not following UI light/dark theme. Fixed in Phase 4.6 via `--tp-*` custom properties keyed off the same `dark` class `theme.js` already toggles.
- Generated image not reaching the frame edge. Root cause was not the rounded corners (initial suspicion) — it was the frame's 1px border insetting the content box against which `aspect-ratio` resolved, producing a sub-pixel mismatch against the viewBox ratio. Fixed by replacing the border with an inset ring that paints over the image rather than displacing it.
- Right-edge vertical band. Raised in Phase 5.11 and closed then as *not currently reproducing*; reopened in Phase 6.10 against the "Rocky planet" preset and closed there on a confirmed root cause.

  **Not the geometry.** The reopening hypothesis was that terrain polygons stop short of `x = W` for some archetype/aspect combination, leaving a strip where only an overlay paints. Measured and disproved: across 720 combinations (9 archetypes x 5 aspects x 4 seeds x 4 slider sets) every crest layer's polygon reaches exactly `x = 0` and `x = W`, worst-case gap 0.0000. The rendered SVG is also clean at the edge — 45 archetype x aspect scenes rasterized with librsvg at both 1:1 and display scale showed no anomalous column. The **exported file was never affected**; this was only ever the on-page preview.

  **Actual cause.** Every full-canvas shape ended exactly on the viewBox edge, and the outermost `<svg>` clips to its element box by default — so the scene's own outer edge and the clip that trims it sat on the same boundary. When the canvas frame's edge lands *between* device pixels, both get antialiased there, the outermost device-pixel column ends up covered twice at a fraction each, and the frame's own `bg-surface-sunken` backdrop fills what is left. Confirmed rather than inferred: recolouring that backdrop magenta turned the column magenta. Because the backdrop is a flat neutral and each layer contributes its own luminance, the result is a pale, desaturated column that tracks the terrain beside it row by row without its hue — the reported signature exactly.

  **Trigger, and how broad it is.** Nothing to do with Dominant peak, Cine 2.39:1, the seed, or any Scene/Colour/Lighting control — it reproduces on all nine archetypes and all five aspects. What it needs is a **fractional effective devicePixelRatio** (OS display scaling at 125/150/175%, or any browser zoom on any display) together with a viewport width that puts the frame's edge off the device grid. At devicePixelRatio 1 or 2 with the frame on whole pixels it does not occur at all, which is why it came and went and why the Phase 5.11 investigation could not pin it. It is **right-edge-only** whenever the frame's left edge happens to land on a whole device pixel and its right edge does not — the common case, since the left edge sits at a fixed 16px gutter while the right one follows the viewport width. Confirmed directly against Joel's own environment: his display runs at an exact 2x scale (clean integer, no artifact expected there), and the bug did reproduce in VS Code's built-in Simple Browser but not in standalone Firefox at the same settings — consistent with VS Code's webview introducing its own effective fractional scale independent of the OS-level DPR.

  **Fix** (Phase 6.10), two halves that only work together: `EDGE_BLEED` in `utils.js` carries every full-canvas fill past the viewBox on all four sides — the closed polygons and the sky/haze/valley-mist rects, never the crest `line`, so shadow splits and mist anchors are untouched — and `overflow: visible` on `#landscape` in `style.css` hands the clipping to the frame so there is one antialiased edge instead of two. The sky and haze gradients moved to `userSpaceOnUse` at the same time, or bleeding their rects would have stretched the colour ramp with them.

  **Measured result.** Live app, same 45 archetype x aspect scenes at the same viewport and fractional devicePixelRatio, before and after. How far the edge column sits from the scene colour beside it: median **109 -> 28.5**, p90 **148 -> 81**, max **166 -> 85**. How much chroma it loses — the desaturation that made it read as a grey band rather than as an edge: median **4 -> 0**, max **90 -> 52**. What remains is the frame's ordinary antialiasing against the page background, which is what any rounded box does at a fractional position. Zero console errors across both runs.

  **Regression check.** 45 archetype x aspect exports rasterized before and after are identical except the outermost row/column — which is the fix — plus a ≤2/255 rounding shift attributable entirely to the gradient-units change, isolated by re-running the whole matrix with the bleed set to 0. On a representative scene that is 543,007 pixels bit-identical, 108,362 differing by 1, 87 by 2, and 1,248 by 78: the full bottom row, which previously rendered as a half-covered blend and now renders as terrain.
